# EFS Namespace Provisioning Mode 요구사항 문서

## 1. 소개

### 1.1 목적
본 문서는 AWS EFS CSI Driver에 네임스페이스별로 격리된 EFS 파일 시스템을 프로비저닝하는 새로운 `efs-ns` 모드의 요구사항을 정의합니다.

### 1.2 범위
이 기능은 Kubernetes 네임스페이스별로 독립적이고 격리된 EFS 파일 시스템을 자동으로 생성하고 관리할 수 있는 동적 프로비저닝 모드를 제공합니다.

### 1.3 배경
기존 `efs-ap` 모드는 단일 EFS 파일 시스템 내에 Access Point를 생성하여 볼륨을 프로비저닝합니다. 새로운 `efs-ns` 모드는 네임스페이스별로 완전히 독립된 EFS 파일 시스템을 생성하여 더 강력한 격리와 독립성을 제공합니다.

## 2. 기능 요구사항

### 2.1 StorageClass 지원

**사용자 스토리:** 클러스터 관리자로서, 네임스페이스별로 격리된 EFS 파일 시스템을 생성하는 StorageClass를 정의하고 싶다.

#### 수락 기준

1. WHEN provisioningMode가 'efs-ns'로 설정된 StorageClass가 생성되면 THEN 시스템은 네임스페이스별 EFS 격리 모드를 활성화해야 한다
2. IF StorageClass에 provisioningMode가 'efs-ns'로 지정되면 THEN fileSystemId 파라미터는 선택사항이어야 한다
3. WHEN 유효한 efs-ns StorageClass가 존재하면 THEN PVC 생성 시 자동으로 네임스페이스별 EFS가 프로비저닝되어야 한다

### 2.2 네임스페이스별 EFS 파일 시스템 생성

**사용자 스토리:** 개발자로서, PVC를 생성할 때 내 네임스페이스에 전용 EFS 파일 시스템이 자동으로 생성되기를 원한다.

#### 수락 기준

1. WHEN 네임스페이스에서 처음으로 efs-ns StorageClass를 사용하는 PVC가 생성되면 THEN 해당 네임스페이스 전용 EFS 파일 시스템이 새로 생성되어야 한다
2. IF 동일한 네임스페이스에서 추가 PVC가 생성되면 THEN 기존에 생성된 네임스페이스 전용 EFS 파일 시스템을 재사용해야 한다
3. WHERE 네임스페이스별 EFS가 생성될 때 THEN 적절한 태그가 자동으로 적용되어야 한다:
   - `kubernetes.io/cluster/<cluster-id>`: 클러스터 식별
   - `kubernetes.io/namespace`: 네임스페이스 이름
   - `kubernetes.io/provisioning-mode`: "efs-ns"
4. WHILE EFS 파일 시스템이 생성 중일 때 THEN PVC는 Pending 상태를 유지해야 한다

### 2.3 Access Point 관리

**사용자 스토리:** 개발자로서, 네임스페이스별 EFS 내에서 각 PVC마다 독립적인 Access Point가 생성되기를 원한다.

#### 수락 기준

1. WHEN PVC가 생성되면 THEN 네임스페이스 EFS 내에 고유한 Access Point가 생성되어야 한다
2. IF directoryPerms가 지정되면 THEN Access Point 루트 디렉토리에 해당 권한이 적용되어야 한다
3. WHEN uid/gid 또는 gidRange가 지정되면 THEN Access Point에 적절한 POSIX 권한이 설정되어야 한다
4. WHERE basePath가 지정되면 THEN Access Point가 해당 경로 하위에 생성되어야 한다

### 2.4 크로스 계정 마운트 지원

**사용자 스토리:** 운영자로서, 다른 AWS 계정의 EFS를 네임스페이스별로 마운트할 수 있어야 한다.

#### 수락 기준

1. WHEN provisioner secret이 지정되면 THEN 크로스 계정 EFS 생성이 지원되어야 한다
2. IF az 파라미터가 지정되면 THEN 해당 가용 영역의 마운트 타겟이 사용되어야 한다
3. WHERE 크로스 계정 마운트가 구성되면 THEN 적절한 IAM 권한이 검증되어야 한다

### 2.5 리소스 정리

**사용자 스토리:** 클러스터 관리자로서, 네임스페이스가 삭제될 때 관련 EFS 리소스가 적절히 정리되기를 원한다.

#### 수락 기준

1. WHEN 네임스페이스의 마지막 PVC가 삭제되면 THEN 모든 Access Point가 삭제되어야 한다
2. IF 정리 정책이 'delete'로 설정되면 THEN 네임스페이스 삭제 시 EFS 파일 시스템도 삭제되어야 한다
3. WHERE 정리 정책이 'retain'으로 설정되면 THEN EFS 파일 시스템은 보존되어야 한다

## 3. 비기능 요구사항

### 3.1 보안 요구사항

**사용자 스토리:** 보안 관리자로서, 네임스페이스 간 데이터 격리가 완벽하게 보장되기를 원한다.

#### 수락 기준

1. WHEN 네임스페이스별 EFS가 생성되면 THEN 다른 네임스페이스에서 접근할 수 없어야 한다
2. IF 사용자가 다른 네임스페이스의 EFS에 접근을 시도하면 THEN 접근이 거부되어야 한다
3. WHERE 암호화가 활성화되면 THEN 모든 데이터가 전송 중 및 저장 시 암호화되어야 한다
4. WHILE EFS 리소스가 존재하면 THEN 적절한 IAM 역할과 정책이 유지되어야 한다

### 3.2 성능 요구사항

**사용자 스토리:** 개발자로서, 네임스페이스별 EFS 프로비저닝이 빠르고 효율적이기를 원한다.

#### 수락 기준

1. WHEN PVC가 생성되면 THEN EFS 프로비저닝이 5분 이내에 완료되어야 한다
2. IF 기존 네임스페이스 EFS가 존재하면 THEN Access Point 생성은 30초 이내에 완료되어야 한다
3. WHERE 동시에 여러 PVC가 생성되면 THEN 순차적 처리가 아닌 병렬 처리가 수행되어야 한다

### 3.3 호환성 요구사항

**사용자 스토리:** 클러스터 관리자로서, 새로운 기능이 기존 시스템과 완벽하게 호환되기를 원한다.

#### 수락 기준

1. WHEN efs-ns 모드가 도입되면 THEN 기존 efs-ap 모드와 공존할 수 있어야 한다
2. IF Kubernetes 버전이 1.17 이상이면 THEN efs-ns 모드가 정상 작동해야 한다
3. WHERE CSI Driver 버전이 2.x 이상이면 THEN 모든 기능이 지원되어야 한다
4. WHILE 업그레이드가 수행되면 THEN 기존 볼륨에 영향을 주지 않아야 한다

### 3.4 가용성 요구사항

**사용자 스토리:** 운영자로서, 네임스페이스별 EFS가 높은 가용성을 제공하기를 원한다.

#### 수락 기준

1. WHEN EFS가 생성되면 THEN 다중 가용 영역에 마운트 타겟이 생성되어야 한다
2. IF 한 가용 영역에 장애가 발생하면 THEN 다른 가용 영역을 통해 접근 가능해야 한다
3. WHERE 재시도 로직이 구현되면 THEN 일시적 장애에 대해 자동 복구가 수행되어야 한다

### 3.5 모니터링 및 로깅 요구사항

**사용자 스토리:** 운영자로서, 네임스페이스별 EFS 사용 현황을 모니터링하고 싶다.

#### 수락 기준

1. WHEN EFS 리소스가 생성/삭제되면 THEN 상세한 이벤트 로그가 기록되어야 한다
2. IF 오류가 발생하면 THEN 구체적인 오류 메시지와 해결 방안이 로깅되어야 한다
3. WHERE 메트릭이 수집되면 THEN Prometheus 형식으로 노출되어야 한다
4. WHILE 운영 중일 때 THEN 네임스페이스별 용량 사용량이 추적되어야 한다

## 4. 기술 구현 요구사항

### 4.1 컨트롤러 서비스 확장

**사용자 스토리:** 개발자로서, CSI 컨트롤러가 네임스페이스별 EFS 생성을 지원하기를 원한다.

#### 수락 기준

1. WHEN CreateVolume이 호출되면 THEN provisioningMode를 확인하여 적절한 프로비저닝 로직을 실행해야 한다
2. IF provisioningMode가 'efs-ns'이면 THEN 네임스페이스별 EFS 생성 로직이 실행되어야 한다
3. WHERE EFS 생성이 필요하면 THEN AWS EFS API를 사용하여 파일 시스템을 생성해야 한다
4. WHILE 생성 중일 때 THEN 상태를 추적하고 적절한 재시도 로직을 구현해야 한다

### 4.2 네임스페이스 EFS 매핑 관리

**사용자 스토리:** 시스템으로서, 네임스페이스와 EFS 간의 매핑을 효율적으로 관리해야 한다.

#### 수락 기준

1. WHEN 네임스페이스 EFS 매핑이 생성되면 THEN ConfigMap 또는 CRD에 저장되어야 한다
2. IF 매핑 정보가 손실되면 THEN AWS 태그를 통해 복구할 수 있어야 한다
3. WHERE 매핑 조회가 필요하면 THEN 효율적인 캐싱 메커니즘이 사용되어야 한다
4. WHILE 매핑이 업데이트되면 THEN 동시성 제어가 적절히 처리되어야 한다

### 4.3 AWS API 통합

**사용자 스토리:** 시스템으로서, AWS EFS API와 안정적으로 통합되어야 한다.

#### 수락 기준

1. WHEN AWS API를 호출하면 THEN 적절한 재시도와 백오프 전략이 적용되어야 한다
2. IF API 한도에 도달하면 THEN 요청이 큐잉되고 점진적으로 처리되어야 한다
3. WHERE IAM 권한이 필요하면 THEN 최소 권한 원칙이 적용되어야 한다
4. WHILE API 호출 중일 때 THEN 타임아웃과 오류 처리가 적절히 구현되어야 한다

## 5. 구성 파라미터 사양

### 5.1 StorageClass 파라미터

| 파라미터 | 타입 | 기본값 | 필수 | 설명 |
|---------|------|--------|------|------|
| provisioningMode | string | - | 필수 | 'efs-ns'로 설정하여 네임스페이스별 격리 모드 활성화 |
| fileSystemId | string | - | 선택 | 기존 EFS 사용 시 지정 (미지정 시 자동 생성) |
| directoryPerms | string | "700" | 필수 | Access Point 루트 디렉토리 권한 |
| uid | string | - | 선택 | POSIX 사용자 ID |
| gid | string | - | 선택 | POSIX 그룹 ID |
| gidRangeStart | string | "1000" | 선택 | POSIX 그룹 ID 범위 시작 |
| gidRangeEnd | string | "2000" | 선택 | POSIX 그룹 ID 범위 종료 |
| basePath | string | "/dynamic_provisioning" | 선택 | Access Point 생성 기본 경로 |
| subPathPattern | string | "${.PV.name}" | 선택 | Access Point 하위 경로 패턴 |
| ensureUniqueDirectory | bool | true | 선택 | UUID 추가를 통한 디렉토리 고유성 보장 |
| az | string | - | 선택 | 크로스 계정 마운트용 가용 영역 |
| reuseAccessPoint | bool | false | 선택 | PVC 이름 기반 Access Point 재사용 |
| performanceMode | string | "generalPurpose" | 선택 | EFS 성능 모드 (generalPurpose/maxIO) |
| throughputMode | string | "bursting" | 선택 | EFS 처리량 모드 (bursting/provisioned/elastic) |
| provisionedThroughputInMibps | string | - | 선택 | 프로비저닝된 처리량 (throughputMode가 provisioned일 때) |
| encrypted | bool | true | 선택 | EFS 암호화 활성화 |
| kmsKeyId | string | - | 선택 | KMS 키 ID (암호화 사용 시) |
| lifecyclePolicy | string | - | 선택 | EFS 수명 주기 정책 |
| backupPolicy | string | "ENABLED" | 선택 | AWS Backup 정책 |
| cleanupPolicy | string | "retain" | 선택 | 네임스페이스 삭제 시 정리 정책 (retain/delete) |

### 5.2 Provisioner Secret 파라미터

| 파라미터 | 타입 | 필수 | 설명 |
|---------|------|------|------|
| csi.storage.k8s.io/provisioner-secret-name | string | 선택 | 크로스 계정 접근용 시크릿 이름 |
| csi.storage.k8s.io/provisioner-secret-namespace | string | 선택 | 시크릿이 있는 네임스페이스 |

## 6. 통합 요구사항

### 6.1 기존 CSI Driver와의 통합

**사용자 스토리:** 개발자로서, 새로운 기능이 기존 CSI Driver와 원활하게 통합되기를 원한다.

#### 수락 기준

1. WHEN efs-ns 모드가 추가되면 THEN 기존 인터페이스를 변경하지 않아야 한다
2. IF 기존 efs-ap 모드가 사용 중이면 THEN 동시에 efs-ns 모드도 사용 가능해야 한다
3. WHERE 공통 코드가 있으면 THEN 재사용 가능한 모듈로 분리되어야 한다
4. WHILE 통합 테스트가 실행되면 THEN 모든 모드가 정상 작동해야 한다

### 6.2 Kubernetes API 통합

**사용자 스토리:** 시스템으로서, Kubernetes API와 적절히 통합되어야 한다.

#### 수락 기준

1. WHEN 네임스페이스 이벤트가 발생하면 THEN 적절한 리스너가 반응해야 한다
2. IF RBAC 권한이 필요하면 THEN 최소 필요 권한만 요청해야 한다
3. WHERE 상태 업데이트가 필요하면 THEN PVC/PV 상태가 적절히 반영되어야 한다
4. WHILE 워치 메커니즘이 작동하면 THEN 리소스 변경사항이 실시간으로 감지되어야 한다

### 6.3 모니터링 시스템 통합

**사용자 스토리:** 운영자로서, 기존 모니터링 시스템과 통합되기를 원한다.

#### 수락 기준

1. WHEN 메트릭이 생성되면 THEN Prometheus 형식으로 노출되어야 한다
2. IF CloudWatch 통합이 활성화되면 THEN 관련 메트릭이 푸시되어야 한다
3. WHERE 로그가 생성되면 THEN 구조화된 JSON 형식이어야 한다
4. WHILE 추적이 활성화되면 THEN OpenTelemetry 표준을 따라야 한다

## 7. 테스트 요구사항

### 7.1 단위 테스트

**사용자 스토리:** 개발자로서, 모든 핵심 기능에 대한 단위 테스트가 있기를 원한다.

#### 수락 기준

1. WHEN 새로운 코드가 추가되면 THEN 80% 이상의 코드 커버리지를 유지해야 한다
2. IF 핵심 로직이 변경되면 THEN 관련 단위 테스트가 업데이트되어야 한다
3. WHERE 엣지 케이스가 있으면 THEN 테스트 케이스로 커버되어야 한다
4. WHILE CI/CD가 실행되면 THEN 모든 단위 테스트가 통과해야 한다

### 7.2 통합 테스트

**사용자 스토리:** 테스터로서, 전체 시스템이 통합되어 정상 작동하는지 확인하고 싶다.

#### 수락 기준

1. WHEN 통합 테스트가 실행되면 THEN 실제 AWS 환경에서 테스트되어야 한다
2. IF 네임스페이스 생성/삭제 시나리오가 테스트되면 THEN EFS 리소스가 적절히 관리되어야 한다
3. WHERE 동시성 테스트가 수행되면 THEN 레이스 컨디션이 발생하지 않아야 한다
4. WHILE 장애 시나리오가 테스트되면 THEN 시스템이 gracefully 복구되어야 한다

### 7.3 E2E 테스트

**사용자 스토리:** QA 엔지니어로서, 실제 사용 시나리오를 E2E로 테스트하고 싶다.

#### 수락 기준

1. WHEN E2E 테스트가 실행되면 THEN 전체 워크플로우가 검증되어야 한다
2. IF 다중 네임스페이스 시나리오가 테스트되면 THEN 격리가 유지되어야 한다
3. WHERE 성능 테스트가 수행되면 THEN SLA 요구사항을 충족해야 한다
4. WHILE 스트레스 테스트가 실행되면 THEN 시스템이 안정적으로 동작해야 한다

### 7.4 보안 테스트

**사용자 스토리:** 보안 엔지니어로서, 보안 취약점이 없는지 확인하고 싶다.

#### 수락 기준

1. WHEN 보안 스캔이 실행되면 THEN 알려진 취약점이 발견되지 않아야 한다
2. IF 권한 테스트가 수행되면 THEN 최소 권한 원칙이 검증되어야 한다
3. WHERE 침투 테스트가 수행되면 THEN 네임스페이스 간 격리가 유지되어야 한다
4. WHILE 암호화 테스트가 실행되면 THEN 모든 데이터가 적절히 보호되어야 한다

## 8. 문서화 요구사항

### 8.1 사용자 문서

**사용자 스토리:** 사용자로서, 새로운 기능을 쉽게 이해하고 사용할 수 있는 문서가 필요하다.

#### 수락 기준

1. WHEN 문서가 작성되면 THEN 명확한 예제와 함께 제공되어야 한다
2. IF 설정 옵션이 있으면 THEN 각 옵션에 대한 상세 설명이 포함되어야 한다
3. WHERE 문제 해결 가이드가 있으면 THEN 일반적인 문제와 해결책이 포함되어야 한다
4. WHILE 문서가 유지보수되면 THEN 버전별 변경사항이 명확히 기록되어야 한다

### 8.2 API 문서

**사용자 스토리:** 개발자로서, API 변경사항과 새로운 인터페이스에 대한 문서가 필요하다.

#### 수락 기준

1. WHEN API가 추가/변경되면 THEN OpenAPI 스펙이 업데이트되어야 한다
2. IF 새로운 파라미터가 추가되면 THEN 타입, 기본값, 검증 규칙이 문서화되어야 한다
3. WHERE 에러 코드가 정의되면 THEN 의미와 해결 방법이 설명되어야 한다
4. WHILE API 버전이 관리되면 THEN 하위 호환성이 명시되어야 한다

### 8.3 운영 가이드

**사용자 스토리:** 운영자로서, 프로덕션 환경에서 안정적으로 운영하기 위한 가이드가 필요하다.

#### 수락 기준

1. WHEN 운영 가이드가 작성되면 THEN 모니터링 설정 방법이 포함되어야 한다
2. IF 트러블슈팅 섹션이 있으면 THEN 로그 분석 방법이 설명되어야 한다
3. WHERE 성능 튜닝 가이드가 있으면 THEN 권장 설정값이 제공되어야 한다
4. WHILE 백업/복구 절차가 문서화되면 THEN 단계별 지침이 명확해야 한다

## 9. 마이그레이션 및 업그레이드

### 9.1 기존 시스템 마이그레이션

**사용자 스토리:** 관리자로서, 기존 efs-ap 모드에서 efs-ns 모드로 안전하게 마이그레이션하고 싶다.

#### 수락 기준

1. WHEN 마이그레이션이 시작되면 THEN 기존 볼륨은 영향받지 않아야 한다
2. IF 마이그레이션 도구가 제공되면 THEN 데이터 무결성이 보장되어야 한다
3. WHERE 롤백이 필요하면 THEN 이전 상태로 안전하게 복구할 수 있어야 한다
4. WHILE 마이그레이션이 진행되면 THEN 진행 상황이 모니터링되어야 한다

### 9.2 버전 업그레이드

**사용자 스토리:** 관리자로서, CSI Driver를 새 버전으로 안전하게 업그레이드하고 싶다.

#### 수락 기준

1. WHEN 업그레이드가 수행되면 THEN 무중단으로 진행되어야 한다
2. IF 스키마 변경이 있으면 THEN 자동 마이그레이션이 수행되어야 한다
3. WHERE 비호환 변경이 있으면 THEN 명확한 경고가 제공되어야 한다
4. WHILE 업그레이드 중일 때 THEN 기존 워크로드는 정상 작동해야 한다

## 10. 제약사항 및 가정

### 10.1 제약사항

1. Fargate 노드에서는 동적 프로비저닝을 사용할 수 없음
2. Kubernetes 1.17 이상 버전 필요
3. CSI Driver 2.0.0 이상 버전 필요
4. AWS EFS 서비스가 지원되는 리전에서만 사용 가능
5. 네임스페이스당 하나의 EFS 파일 시스템 제한

### 10.2 가정

1. 클러스터에 적절한 IAM 권한이 구성되어 있음
2. VPC와 서브넷이 EFS 마운트 타겟을 지원하도록 구성됨
3. 네임스페이스 이름이 AWS 리소스 명명 규칙을 준수함
4. 충분한 EFS 서비스 할당량이 확보되어 있음
